<objective>
Fix the broken Padding controls in the editor RightPanel. Editing the "P" field
currently writes only the shorthand `padding` MJML attribute, but grapesjs-mjml's
`style-default` ships LONGHAND paddings (`padding-top/right/bottom/left`) on the
model. At MJML compile longhand overrides shorthand, so the canvas never re-renders
when the user edits padding — a preview/export divergence (export is accidentally
correct because getHtml omits default-valued longhands).

Fix: when the user edits `padding`, mirror the CSS shorthand into the four longhand
styles on the same component so the canvas re-renders correctly. Clearing the field
removes the longhands so the plugin's default padding reasserts.

Purpose: restore WYSIWYG padding editing (the canvas must reflect what the user sets).
Output: expansion logic in `editorConfig.ts` + a load guard in `actions.ts`.
</objective>

`onEditor`, e.g. `editor.on('component:selected', ...)` and

MJML_DEFAULT_PADDING already writes explicit SHORTHAND padding on dropped
sections/text/image/button (e.g. "20px 0"). So dropped components carry shorthand
`padding` but no longhands — this is the exact state the fix must handle safely.

From actions.ts:
- `load(editor)` calls `editor.loadProjectData(...)`.
- `getExportMjml(editor)` calls `editor.loadProjectData(snapshot)` in a `finally`.
- `assertRoundTrip(editor)` and `window.__ddroiddAssertRoundTrip()` prove save→load
  is byte-identical (the Phase-1 gate).

  so importing a new guard getter from actions.ts is in-pattern.

GrapesJS component style API (0.22.16):
- `component.getStyle()` → Record<string,string> (returns `{ padding: '10px 25px', ... }`).
- `component.addStyle({ 'padding-top': '10px', ... })` — merge styles, re-renders canvas.
- `component.removeStyle('padding-top')` — remove one style property.
- Event `component:styleUpdate:padding` fires (component, ...) when the padding style
  changes via the StyleManager. Read the target from the first event arg, falling back
  to `editor.getSelected()`.

<task type="auto">
  <name>Task 2: Mirror padding shorthand into longhands in editorConfig.ts</name>
  <files>app/client/src/editor/editorConfig.ts</files>
  <action>
Import `isLoadingProject` from './actions' (extend the existing import line).

Add a pure helper `const parsePaddingShorthand = (value: string): [string, string, string, string] | null` that splits the CSS shorthand on whitespace and returns
[top, right, bottom, left] per the 1/2/3/4-value CSS rules:
- 1 value: all four equal.
- 2 values: [v1 v2] → top=bottom=v1, right=left=v2.
- 3 values: [v1 v2 v3] → top=v1, right=left=v2, bottom=v3.
- 4 values: top=v1, right=v2, bottom=v3, left=v4.
Return null for 0 or >4 tokens (defensive). Keep it React-free and side-effect-free.

In `onEditor`, register a listener (near the existing `block:drag:stop` listener):
`editor.on('component:styleUpdate:padding', (component) => {...})`.

Handler logic:
1. Bail immediately if `isLoadingProject()` is true — never mutate during a load
   (this is what keeps the Phase-1 round-trip gate green).
2. Resolve the target component from the event arg, falling back to
   `editor.getSelected()`. Bail if none.
3. Add a module-scoped boolean re-entrancy guard (`let expandingPadding = false;`).
   Bail if already true; otherwise set it true, run the body in try/finally, reset it
   in finally. (Re-entrancy is largely avoided by construction — we only write the
   four longhands, and `:padding-top` etc. do NOT match this `:padding` listener — but
   keep the flag as cheap insurance.)
4. Read `const paddingValue = component.getStyle()['padding'];`.
   - If it is falsy / empty string: `component.removeStyle('padding-top')` for each of
     the four longhands, so the plugin's default padding reasserts (this is the
     intended "reset to default" on clear, NOT reset to zero).
   - Else parse via `parsePaddingShorthand`. If it returns null, do nothing. Otherwise
     `component.addStyle({ 'padding-top': top, 'padding-right': right,
     'padding-bottom': bottom, 'padding-left': left })`.

Do NOT touch `inner-padding` — the plugin has no `inner-padding-*` longhands, so its
shorthand already renders correctly (verified in the diagnosis). Do NOT write the
shorthand `padding` back inside the handler (it is already set — that is what fired the
event; re-writing it would risk a loop).

Follow code-style.md: `const` arrow functions, `type` over `interface`, curly braces on
every `if`, early return on the fail condition.
