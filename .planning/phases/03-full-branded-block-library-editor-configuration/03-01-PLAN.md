<interfaces>
Verified facts (from 03-RESEARCH.md, source-checked against installed bundles):
- GrapesJS 0.22.16 core parser recognizes the literal prefix `data-gjs-` and moves any such
  attribute into the component MODEL property at drop/parse time (NOT into DOM/MJML attrs).
  `'true'`/`'false'` → booleans; `'[...]'` strings → JSON.parse'd arrays.
- Locking flag assignment (per user's locked decision, uniform rule):
    outer `<mj-section>`  → `data-gjs-draggable="false" data-gjs-removable="false"`
    every `<mj-column>`   → `data-gjs-droppable='["mj-text","mj-image"]'`  (ARRAY allowlist, NOT boolean)
    `<mj-text>`/`<mj-image>` → NO data-gjs-* attrs (stay editable/movable/removable at defaults)
- `droppable` as a plain boolean `false` also blocks reordering existing children; the array form
  discriminates by dragged type, so existing text/image children still reorder (RESEARCH Pitfall 4).
- `app/server/scripts/verify-blocks.ts` imports from `../../client/src/blocks/*` — STALE. The
  `260705-h8h` refactor moved blocks to `app/client/src/editor/blocks/`. `verify-compile.ts` and
  `verify-parity.ts` already use the correct `editor/blocks/` path — DO NOT touch those two.
- `verify-blocks.ts` compiles each block's RAW content string directly through `mjml` (bypassing
  GrapesJS's parser), so `data-gjs-*` attrs are NOT stripped in that path (RESEARCH Pitfall 2) —
  they reach `mjml2html()` as literal attrs. In production they never reach the compiler (GrapesJS
  strips them at drop). So a `verify:blocks` error here means the GATE tests an input that never
  occurs in production.
- hero.ts currently has TWO top-level `<mj-section>` blocks (hero content + a dashed-divider section).
  Both are branded structure → both get the outer-section lock flags.
- Never self-close mj-* tags in block content strings (grapesjs.md). This task only ADDS attributes
  to existing open tags — do not convert any tag to self-closing.
</interfaces>
